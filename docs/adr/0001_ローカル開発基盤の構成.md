# 0001. ローカル開発基盤の構成（Docker Compose + Firebase Emulator Suite + ホスト側Flutter）

- ステータス: 承認
- 日付: 2026-11-05
- 作成者: はるたぬ
- 関連: docs/02_システム設計書.md, docs/04_DB設計書.md, docs/07_環境構築手順書.md, docs/08_Docker_Makefile運用.md

## コンテキスト

- 本番アーキテクチャは Firebase/GCP 中心（Firebase Auth、Firestore、Storage、Realtime Database、Cloud Run API、Firebase Hosting）であり、ローカルで再現する必要がある。
- 医療情報（PHI）を扱うため、開発時から本番GCPプロジェクトや実データに触れない構成が必要（`mmr-dev` は完全合成データ方針）。
- 実装コードがまだ存在しない段階で環境だけを先行整備するため、アプリが追加された時点で自動的に起動対象へ組み込まれる構造が求められた。
- 構成要素は4つ：Firebaseエミュレータ群、Cloud Run API相当（Node.js/TypeScript）、Next.js（TypeScript + Tailwind CSS、Firebase Hosting配信）病院ポータル、Flutter（Dart）患者アプリ（Android/iOS/Web）。

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A. 全てホスト直インストール | firebase-tools/java/Node/Flutterを各開発者が入れる | 起動が速い・馴染みがある | Java/Nodeバージョン差異で環境が揺れる。再現性が低い |
| B. 全てDocker | Flutter含め全サービスをコンテナ化 | 完全に再現可能 | iOS/Androidシミュレータ・実機転送はコンテナ化不能。Flutterイメージが巨大でWeb開発のホットリロードも不安定 |
| C. ハイブリッド（採用） | エミュレータ・API・病院ポータルはDocker、患者Flutterはホスト実行 | 再現性と実用性の両立 | Flutter SDKは各開発者がインストールする必要がある |

## 決定

- **Firebase Emulator Suite（Auth/Firestore/RTDB/Storage + Emulator UI）をDockerコンテナで常設**する（`firebase` サービス）。
- **API・病院ポータルは `services/api`・`apps/hospital` に実装が置かれた時点でComposeが起動対象に含める**。起動可否は `package.json`/`pubspec.yaml` の存在をMakefileが検出して自動決定する。
- **患者FlutterアプリはDocker化せず、`make up` がホスト側で `flutter run -d web-server` をバックグラウンド起動**する。
- エミュレータは `demo-mmr-dev` というダミープロジェクトIDで動かし、本番GCPに接続しない。

## 理由

- FlutterはiOS/Android実機・シミュレータが開発の主軸でありコンテナ化の恩恵が薄い。一方でWeb開発サーバとしては `flutter run -d web-server` がホストでそのまま使えるため、Dockerで重ねる意味がない。
- Firebase Emulator SuiteはJava・Node・firebase-toolsの組合せが必要で、開発者間の差異が出やすい部分をコンテナに閉じ込める効果が大きい。
- Security Rules（deny-by-default）は docs/04_DB設計書 §7 の最小権限例をそのまま `firebase/` に配置し、実装開始時点から安全側の既定とした。

## 結果・影響

- `make up` 一発でエミュレータ＋実装済みアプリ＋ファイル監視が起動する。未実装アプリは自動スキップされ、実装追加後は検出して自動的に起動対象になる。
- エミュレータデータは名前付きボリュームにエクスポートされ、`make down` しても保持される（`make clean` で消去）。
- API/病院ポータルのDockerfileは `dev` ターゲット前提のマルチステージで、本番向け `prod` ターゲットは実装確定後に調整が必要。

## 再評価条件

- Flutter Webの開発をチーム標準でコンテナ化したくなった時（Dev Container等への移行検討）。
- APIの言語・フレームワークがNode.js以外に決まった時（`docker/api/Dockerfile` の差し替え）。
