# 0002. ローカルのシークレット・環境変数管理（.env.local / .secret.local）

- ステータス: 承認
- 日付: 2026-11-05
- 作成者: はるたぬ
- 関連: docs/02_システム設計書.md（NFR-12）, docs/07_環境構築手順書.md

## コンテキスト

- 設計上、秘密情報は本番では GCP Secret Manager に置く（NFR-12）。
- ただしローカル開発は Firebase Emulator 中心でGCPプロジェクトに接続しないため、Secret Manager を立てるのは過剰であり、認証情報の配布自体がリスクになる。
- 開発者は Places API キー・LLM API キー・サーバ側HMAC鍵などを何らかの形でローカルに置く必要がある。

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A. ローカルでもSecret Manager | GCPプロジェクトを立てて参照 | 本番と同じ仕組み | GCP認証・プロジェクト作成がセットアップの壁になる。オフライン開発不可 |
| B. 1つの `.env` に集約 | 慣習的なenvファイル1本 | 単純 | 秘密値と非秘密値の区別がつかず、誤ってログ・issueに貼るリスク |
| C. `.env.local` / `.secret.local` の2分離（採用） | 非秘匿と秘匿をファイル単位で分ける | 秘匿だけの差し替え・取り扱い注意が明確。make/compose両方から読める | ファイルが2つに増える。共有は別チャネルが必要 |

## 決定

- **非シークレットは `.env.local`、シークレットは `.secret.local`** に置き、ローカル開発では Secret Manager の代替とする。
- どちらも `.gitignore` でコミット禁止とし、雛形として `.env.example` / `.secret.example` をリポジトリに置く。`make env`（`make up` に内包）で初回自動コピーする。
- Makefile は `-include` で両ファイルを読み込み、docker-compose は `env_file`（`required: false`）でコンテナへ渡す。
- 本番・stg環境はこの方式を使わず Secret Manager を使う。`.secret.local` に本番の値・実患者データを置かない。

## 理由

- 秘匿と非秘匿を分離することで、「`.secret.local` の内容をissue・ログ・PRに貼らない」という単純で守りやすいルールになる。
- エミュレータ中心の開発ではほとんどの秘密値はダミーで済むため、初回セットアップの摩擦を最小化できる。
- docker compose の `env_file` と make の `-include` の両方が `KEY=value` 形式を読めるため、1ファイルで二系統に供給できる。

## 結果・影響

- 値の共有は別チャネル（パスワードマネージャの共有ボルト等）で行う運用が必要。README・docs/07 にその旨を明記した。
- `KEY=value`・引用符なし・行頭 `#` コメントという形式制約がある（make が makefile 構文として解釈するため）。

## 再評価条件

- stg/本番相当の環境をローカルから叩く運用が必要になった時（Secret Manager 連携ツールへの移行）。
- チーム拡大で秘密値のローテーション管理が必要になった時。
