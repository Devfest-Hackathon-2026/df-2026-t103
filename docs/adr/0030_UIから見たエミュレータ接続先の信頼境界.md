# 0030. UI から見たエミュレータ接続先の信頼境界

- ステータス: 提案
- 日付: 2026-11-09
- 作成者: OpenCode
- 関連: Issue #141, ADR-0013, ADR-0017, `apps/hospital/lib/client-config.ts`, `services/api/src/config.ts`

## コンテキスト

Issue #141 は、デモ UI が接続してよい接続先を安全に判断できる構成を求めている。現行実装を確認した事実は次のとおり。

- 病院 UI の `NEXT_PUBLIC_*` 設定はブラウザへ配布される公開設定である。`validateClientConfig` はデモ時に project ID と loopback URL を要求し、API 宛先を絞るが、その URL の先で応答する相手が Firebase Emulator / ローカル API であることを証明しない。設定値は秘密でも認証情報でもない。
- `GET /healthz` は認証なしのロードバランサ向け readiness probe である。Firestore の read 成否とサーバ設定由来の `emulator` 値を返すだけで、接続先の真正性、Auth / Storage / RTDB の Emulator 稼働、または UI が意図した API と通信していることを証明しない。HTTP 応答の `emulator: true` も自己申告である。
- API の `loadConfig` はサーバ起動時に Firebase Auth / Firestore / Storage / RTDB の Emulator host の全指定、host/port allowlist、demo project 条件を検査し、部分設定・実 project との混在等を拒否する。これはサーバ側設定の整合性検査であり、UI の申告や `/healthz` によって緩和してはならない。
- `loadConfig` は Emulator 設定と本番環境の組み合わせを拒否するよう更新された。これは起動設定の検査であり、既存 Cloud Run 環境の設定・稼働状態を確認したものではない。

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A | ブラウザ公開設定または `/healthz` の `emulator` 値で Emulator 接続を認定する | UI 側の判定が簡単 | 改変可能なクライアント設定・自己申告応答であり、相手の真正性を証明しない。誤接続時に安全境界として機能しない |
| B | UI の明示 opt-in と接続先 allowlist は誤設定防止の補助に限定し、API は独立したサーバ設定で fail-closed にする（提案） | クライアントとサーバの責務を分け、client claim に依存しない。現行 API 起動時検査と整合する | loopback 到達先そのものの真正性は UI から証明できない。ローカル開発環境と Emulator プロセスの信頼は運用前提として残る |
| C | Emulator を使わない架空データ専用 UI とし、外部 API / Firebase を初期化しない | 接続先事故の面を最小化できる | 実 API と結合したデモ・動作確認には使えない。接続を伴うデモの代替にはならない |

## 決定

**B を提案する。** UI の Emulator 設定は意図しない宛先への接続を減らすクライアント側ガードとして扱い、接続先の真正性・安全性の証明とは扱わない。接続を伴う UI は明示的なローカル opt-in と狭い宛先 allowlist を維持する。API はクライアントの emulator フラグ、公開設定、`/healthz` 応答に依存せず、自身の環境設定だけで Firebase Emulator 接続を選び、既存の全サービス設定検査に失敗した場合は起動を拒否する。本番 API は Emulator 用設定を拒否し、実 project での App Check permissive を許すため App Check 常時 enforce を保証するものではない。純粋な画面プレビューは可能な限り API / Firebase を初期化しない。

## 理由

- ブラウザに届く設定・コードは利用者側で読取り・改変できる。project ID、`useEmulator` フラグ、固定 API key、あるいは `emulator` 応答値は、相手が Emulator であることを証明する秘密・資格情報・暗号学的 attestation ではない。
- `localhost` / loopback allowlist はリモート宛先への誤接続を抑止するが、同じ端末上の別プロセス、プロキシ、侵害済み端末、ブラウザ拡張等からの偽装を検出しない。したがって「ローカル宛先だから Emulator」と断定しない。
- `/healthz` は readiness 用であり、認証・相互認証・全 Firebase サービス検査を提供しない。応答内容を接続先の認定や fail-open fallback の根拠にしない。
- デモ UI の設定誤りは UX / 運用リスクとして封じ、データ保護の最終境界は API のサーバ側設定・認証・認可・App Check と Firebase Security Rules に置く。UI が Emulator を申告しても API の保護を緩和しない。ただし現行設定は、Emulator なしの production で `APP_CHECK_MODE=permissive` を明示することを拒否せず、常時 enforce とは主張しない。

## 結果・影響

- 実装済みのサーバ側検査（`services/api/src/config.ts`）は Emulator 設定を production 起動時に拒否する。production かつ Emulator なしの明示的 `APP_CHECK_MODE=permissive` は依然可能である。検査が保証するのは設定値の形式・組合せであり、接続先プロセスの真正性、Firebase 以外の外部サービスの宛先、または既存 Cloud Run 環境の実設定・稼働状態までは保証しない。
- 病院 UI の `client-config.ts` による URL / project ID 検査は誤設定防止であり、サーバの安全性証明ではない。`healthz` を使った UI の接続先自動判定や、本番接続失敗時のデモ／Emulator への自動 fallback は追加しない。
- 実 Emulator と API の結合確認は、合成データを使う使い捨てローカル Emulator でのみ行う。共有 Emulator・実クラウド・実データを安全確認に流用しない。
- この ADR は設計範囲と保証限界の記録であり、UI が接続先を暗号学的に認証する機能を追加したものではない。loopback 上のプロセス偽装も防止しない。
- 回帰テストは NODE_ENV=test の Emulator 設定を許容し、production + Emulator 設定を APP_CHECK_MODE 未指定・permissive の双方で拒否する。HMAC の値に依存せず拒否することも確認する。App Check 常時 enforce の保証は対象外である。

## 再評価条件

- UI がローカル以外の Emulator / API に接続する要件が生じ、TLS・認証された接続先識別等の新しい信頼根拠が必要になった場合。
- サーバ側の接続先 allowlist、Firebase サービス利用範囲、または本番の認証・App Check 方針を変更する場合。
